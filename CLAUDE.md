# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Tracer builds interactive citation graphs for academic sources, focused on the humanities, especially history. See `README.md` for the user-facing description.

Core model:

- **Node:** a source (article). It is drawn as a circle whose radius scales with its **total** citation count: how many works cite it according to the provider (`citedByCount`), not only those on the graph. A folded book adds its chapters' counts; works with no count (reference-only) get the minimum size. The sizing metric is one function (`totalCitationCounts` in `graphModel.js`), so it stays easy to swap. The in-graph cited-by count (`inGraphCitationCounts`) is still derived from the edges and shown in the details panel.
- **Edge:** a directed citation (A cites B). Every known citation between any two nodes on the graph is drawn, not only those involving the anchor.
- **Anchor:** the work the user searched for, which the graph is built around. Use this term in code and UI (not "root"). A graph can have several (`graph.anchorIds`, in the order added; the first is the **primary** anchor: first in the URL, its lane centered, its title first in the default name). See "Multiple anchors".
- **Graph build:** from the anchors, fetch citing works (incoming edges) and cited works (outgoing edges), breadth-first. The two directions have **separate depths**, e.g. citing depth 1 and cited depth 3. With several anchors, the first level holds them all, so depth is measured from the nearest anchor and max works is one budget for the whole graph.
- **Multiple anchors:** any work's details offer "Add as anchor" (beside "Make this the anchor", which reads "Make this the only anchor" when there are several), and advanced search "Build with these as anchors". Both are limited by the plan's `anchors` limit (2 on free and signed out, 6 on Scholar; the button is disabled with "Your plan allows up to N anchors"). Adding rebuilds on the anchors plus the new one (`reanchorGraph`). With several, each anchor has "Remove anchor", which rebuilds without it and passes it as `unstick`, so unlike an earlier anchor it isn't sticky and its neighborhood goes (unless something else reaches it). Both push a URL entry and refit.
  - **Neighborhoods:** `anchorNeighborhoods(graph, depths)` (derived, never stored; on the folded view) gives each work the anchors within `max(citingDepth, citedDepth, 1)` citation steps of it, ignoring direction; a work further from all of them gets the nearest, and one not connected to any gets none. Anchors are near only themselves.
  - **Coloring:** with two or more anchors, works are colored by anchor instead of citing/cited (a one-anchor graph looks as before): each anchor in its hue (`--anchor-1` … `--anchor-6`: azure, lobster pink, fern, then three mixes of two), works near one anchor in its tint (`--anchor-N-tint`), works near several as a pie of equal wedges of their tints, clockwise from the top, and works near none in `--node-unlinked`. Icons use `--node-icon-on-anchor-hue`, `-tint` and `--node-icon-on-unlinked`. An anchor's color is its place in `anchorIds`, so removing one shifts the colors of later ones. Measured icon contrast: at least 3.5:1 (azure, light mode) for hues, 5.2:1 for tints, in both themes; azure and its fern mix (hues 1 and 4) are the closest pair. The legend lists each anchor ("… and works near it"), "Near several anchors" and "Not linked to an anchor", and the details list the anchors a work is near, with swatches ("Shared by" for several).
  - **Searches tied to the anchors:** co-citations work per anchor (every anchor's details have the button; the search remembers its anchor and the anchor list, `coCitations.anchorsKey`, and its highlights go when the anchors change). A path search looks for the nearest anchor.
- **Expansion:** clicking a node fetches its citing and cited works and merges them into the existing graph.
- **Layout by year:** time runs along an axis tilted 30° below horizontal by default, with older works up and to the left and newer works down and to the right. Users can rotate the axis from 0° (horizontal) to 90° (vertical). For undated works, a work an anchor cites is treated as older than that anchor, and a work citing an anchor as newer (bounds from several anchors combine). Beyond that, a work is placed older than its dated citers and newer than the dated works it cites (`layoutYears`). A listed year is set aside when at least `MIN_EARLIER_CITERS` (2) of a work's dated citers, and more than half, predate it, since a work can't be cited before it exists: usually it's a reprint or digitization date (OpenAlex dates Nachod's 1897 study 2003). The work is then placed just before its earliest citer, undated neighbors are inferred from that corrected year, year filters use it, and the details panel and tooltip show "Before <year>" with the listed year explained (`LayoutYear.listedYear`, `citedFrom`). Requiring two keeps a single citer with a wrong year from moving a work.
- **Applying options:** changing "Graph depth and size" affects the next search. "Apply to current graph" applies it to the graph on screen by re-anchoring on the current anchors (`reanchorGraph` with the same anchors), so sticky works keep their neighbors. The button is enabled only when the form differs from the options the graph was built with (`graphOptions` in `App`, set when a run finishes).
- **Re-anchoring:** any selected work can become the anchor (the only one). The graph is rebuilt from it at the configured depths, so depth is always measured from the current anchors. **Sticky** works keep their neighbors as if still expanded: the previous anchor(s) and works the user expanded with the button. Works the old build reached only through traversal are dropped unless the new build reaches them.
- **Collapsing:** a work the user expanded (or an earlier anchor) can be collapsed from its details. That's the reverse of the sticky rule: `collapseWorks` removes it (for a book, its chapters too) from `sticky`, and the graph is rebuilt on the same anchors at the depths it was built with (`graphOptions`), through the re-anchor path. Its neighbors stay only if the build or another sticky work reaches them. Anchors and works only the build expanded have no Collapse button, since rebuilding would bring their neighbors back. Collapsing doesn't change the URL or refit the view.
- **Shareable URLs:** the anchors are in the query string, e.g. `?anchor=10.1093%2Fpast%2F50.1.76&cited=2`; several repeat the parameter, primary first (`?anchor=A&anchor=B`), written where the first one was. Blank and repeated anchors are dropped, and only the plan's `anchors` limit are built. A query parameter was chosen over a route because it needs no router and works with the Express SPA fallback.
  - Each anchor is written as its DOI, falling back to the OpenAlex ID, then the Tracer ID (`shareableId`). Tracer IDs only mean something within one database.
  - Build options are written only when they differ from the defaults (`citing`, `cited`, `perNode`, `max`).
  - Manual expansions, sticky works, filters and the axis angle are _not_ in the URL.
- **Book parts:** when a book is on the graph, its chapters (and front matter such as prefaces) aren't nodes of their own. They're listed in a "Chapters" section of the book's details. A work is a part of a book when its DOI is the book's DOI plus a suffix starting with `.`, `_`, `-` or `/` (Cambridge `….005`, Springer `…_5`, De Gruyter `…-005`). Only `book`-type works absorb parts, and anchors are never folded away. Like filters, this is view-only: `foldBookParts` (in `graphModel.js`) derives a view graph in which citations to and from a part are moved onto its book. `App` passes that view to everything drawn or filtered (counts, years, visibility, `GraphView`, `FiltersPanel`), while `graph` keeps every part for fetching, expansion and re-anchoring. Per-chapter counts in the details come from the unfolded graph. Expanding a book also expands each of its chapters (`expandWorks`, two works at a time, merged in one update), since chapter records often have the references that book records lack. The button shows "Expanded" once the book and every chapter are. On Cambridge books, OpenAlex often gives every chapter (front matter included) the whole book's bibliography.
- **Works not on OpenAlex:** references a publisher deposited with Crossref that OpenAlex has no work for (archival sources, older or non-English books) appear as **reference-only** works. They're grey nodes with a question-mark icon, listed as "Not on OpenAlex" in the source-type filter. Their type is `reference-only` (`REFERENCE_ONLY`), whichever direction they joined from. They have no neighbors to fetch, so traversal skips them (`canExpand`), and the details panel shows the citation as printed instead of Expand and "Make this the anchor".
- **Co-citations:** each anchor's details have a "Find Co-Citations" button. It fetches the cited works of every work on the graph that cites that anchor (or one of its chapters; `coCiters`), up to `CO_CITATION_LIMIT` (200, the API's maximum) each, and counts how many of those citers cite each work (once per citer), keeping every count of `MIN_CO_CITERS` (2) or more (`findCoCitations` in `graphModel.js`; the hook runs it as task `cocite`). `applyCoCitations` then shows the works at least a minimum number of citers cite: those not on the graph are added as `cited` works, most co-cited first, up to max works, and each citer's references gain its cited list so the edges draw. Fetching a citer's cited list here doesn't mark it expanded.
  - **Minimum:** a − slider + control above the button, from 2 to the number of citers, defaulting to ⌈√citers⌉ (`defaultMinCoCiters`). After a search it applies at once, from the kept results with no new requests: works the search added (`graph.coCitationAdded`) that no longer qualify are removed, and works that now qualify are added. Works that were on the graph before, that the user expanded (sticky) or pinned, or that an expansion has since found too (`expandWork` takes them out of `coCitationAdded`) are never removed; they only lose their ring. A search fixes the minimum it used (`minCoCitersChoice` in `App`), so the default can't drift as citers come and go. Rebuilding (re-anchor, collapse, options) starts a graph without `coCitationAdded`.
  - **Display:** co-cited works at or above the minimum, new or already on the graph, get a thin ring in the citing works' color (`--node-co-cited`, which is `--node-citing`), as wide as the expanded ring and at its gap, or just outside it on a work that has both (`CO_CITED_RING_*`), listed in the legend, and their details say how many citers cite them. The search (`coCitations` in `App`: `{ anchorId, found, counts, citers }`) is kept only for that anchor: re-anchoring drops the highlights, a new search or opening a saved graph clears them, and they aren't saved (a snapshot's co-cited works reopen as ordinary works).
  - Only citers already on the graph are used, so "works per node" sets how many. On _Manchus and Han_ (20 citers): a minimum of 5 (the default) shows 9 works, 4 shows 15, 7 shows 2, and 2 shows 120.
- **Pinning:** any work can be pinned from its details ("Pin: always show" / "Unpin"). A pinned work is always shown, whatever the filters: `App` passes the `pinned` set to `visibleIds` with the selection. Like filters, it's view state: kept across re-anchoring and collapsing, cleared by a new search, saved with a graph as `view.pinned` (Tracer IDs of works still on the graph), not in the URL. On the canvas a pinned work carries a pin badge on its top right edge, a constant `PIN_BADGE_RADIUS` (9) screen pixels so it reads at any zoom (`--node-pin`, `--node-icon-on-pin`); the legend lists it, and the filters' footer counts pinned works ("Showing 10 of 41 · 1 pinned").
- **Notes:** any work can carry a note, written in its details ("Add note", then "Edit note" / "Delete note"; `WorkNote`). Edits are a draft until "Save note" (or Ctrl/⌘+Enter; Escape cancels), so typing doesn't redraw the graph. `App` holds them as `notes` (Tracer ID → text), view state like pins: kept across re-anchoring and collapsing, cleared by a new search, not in the URL. Notes on works a rebuild dropped are kept (and saved), so they're back if the work returns. On the canvas a noted work carries a notebook badge on its top left edge, the same size as the pin badge (`--node-note`, `--node-icon-on-note`, which follow the pin's colors), and its tooltip adds the note's start; the legend lists it. Saved with a graph as `state.annotations` (see Saved graphs).
- **Provenance:** every `Work` has `referenceProviders`, the providers that have each of its citations (Tracer ID → names): `openalex` (its own reference list), `crossref` (a deposited reference list) or `opencitations` (a citation index), several when several have it. The server derives it from where `toWorks` already found each reference (the provider's record, or `records.<provider>.data.tracerIds`), so cached Sources have it at once; snapshots from before it are dropped when opened (see Snapshots), so the graph rebuilds with it. On the client, `foldBookParts` and `foldAliases` carry it over, and `applyPath` marks path links `openalex`. The details panel's "Where the data comes from" (`DataSources`) names the record's provider and the others that added citations, counts the work's links on the graph by direction, grouped by exactly which providers have each so every link counts once ("15: 13 from OpenAlex only, 2 from both OpenAlex and Crossref"; `graphLinks`, `groupByProviders` in `graph/provenance.js`), and lists the links OpenAlex doesn't have, each selectable.
- **Missing-data warnings:** a work whose reference list is probably incomplete is flagged (`referenceWarning` in `graph/provenance.js`, computed on the folded view, so a book counts its chapters' references): none recorded once `NO_REFERENCES_MIN_CITED` (10) works cite it, or fewer than `FEW_REFERENCES` (5) once `FEW_REFERENCES_MIN_CITED` (100) do, only for types that normally cite (not book reviews, datasets, reference-only works and the like). Without it, a work like Thompson's 1971 article (thousands of citers, no references on OpenAlex) looks like an origin point. It gets a warning badge on the circle's bottom right (`TriangleAlert`, `--node-warning`, which follows the pin's colors, since red reads as a citing work), a tooltip line, a legend entry ("References probably missing") and a sentence in its details naming the providers checked (`describeWarning`). On _Manchus and Han_, 14 of its 20 cited works are flagged: older humanities works OpenAlex has no references for.
- **Language:** every `Work` has `language` (an ISO 639 code, `normalizeLanguage` in `providers/ids.js`, or null) and `languageProvider`. OpenAlex detects it from the title and abstract; Crossref's record (read with the reference list, `getRecord`) has what the publisher deposited, which is often a journal's default (the Chinese Science Bulletin deposits "en" for Chinese titles). So OpenAlex's is used unless it has none, or the two disagree and only Crossref's fits the title's script (`chooseLanguage` in `works/titles.js`). The details panel adds the language to the byline (and as the title's `lang`) and says where it came from; the Filters panel has a "Languages" checklist with counts, an exclusion list like source types (`excludedLanguages`, saved with a graph; works with none are "Unknown language", `languageKey` in `graph/languages.js`).
- **Other titles:** `otherTitles` lists a work's titles worth showing beside the one shown, from Crossref's record: its `original-title` (of a translation, or in the original script), and its deposited title when that's in a different script from OpenAlex's (a romanized title next to Chinese characters, or the reverse), each with its kind and script (`scriptOf`: latin, han, japanese, hangul, cyrillic, …). Titles differing only in form aren't repeated. The details panel shows them under the title ("Original title (Chinese characters)", with a `lang` for CJK text, `langFor`), and the tooltip the first. Only works whose cited list has been fetched (which reads the Crossref record) have them; on the Chinese works tried, Crossref had no second title.
- **Advanced search:** the "Advanced search" link under the search box opens a page that fills everything below the header (`AdvancedSearch`). It searches several fields at once, all of which must match: any field, title, author (as printed), abstract, full text, journal or series and publisher (picked from suggestions, `SuggestPicker`), year range, source types, language, minimum times cited and open access. Results show 25 at a time ("Show more", up to OpenAlex's first 10,000), sortable by relevance (only with text to rank), most cited, newest or oldest. Works are chosen with checkboxes, and the choice is kept across searches. Chosen works are listed in a column on the right, the list scrolling between its summary and buttons (`picked-panel`); below 1100px wide it's a bar under the form and results instead, its chips wrapping. "Build graph" builds around the first chosen work (any other can be made the anchor), then adds and expands the rest (`restore` with them as `expanded`); "Add to current graph" adds and expands them all on the graph on screen (`addWorks` in the hook, `addExpandedWorks` in `graphModel`, which `restoreGraph` also uses). Either way the chosen works are pinned, so filters such as minimum links don't hide one nothing on the graph links to. The page stays mounted (hidden) once opened, so its fields, results and choices survive going back to the graph; the graph stays mounted underneath (the sidebar, canvas and details are `inert` while it's open). It isn't in the URL; Escape or "Back to graph" closes it.
- **Path to the anchor:** a work with no citation path on the graph to an anchor (in a different connected component, `connectedComponents` in `lanes.js`; for example one expanded or added from advanced search) has "Find shortest path to the anchor" in its details. Each anchor counts on its own: with several anchors, a work linked to one but not another can look for the other, and so can an anchor for another anchor it isn't linked to (the path between them). One such anchor gives "Find shortest path to that anchor"; several give a "Path to" choice of the nearest of them or one in particular (`pathTarget` in `App`), sent as the search's targets. The server searches OpenAlex's citations in both directions (`GET /api/works/:id/path?to=`, `shortestPath` in `server/src/works/pathSearch.js`): breadth-first from both ends (the far side starting from every anchor at once, so the path ends at the nearest), growing the side with the smaller frontier by a whole level, so the first meeting gives the shortest length. Among paths of that length it picks the one whose works are cited most in total (`citedByCount`): it collects every work on any shortest path (each side keeps all of a work's parents one level nearer its start), looks up the counts it doesn't know, and keeps each side's most-cited way to each work. The path's works join the graph (`applyPath` in `graphModel`, as citing or cited works by `relationTo` the anchors, its links added to references so the edges draw; not marked expanded or sticky, so a rebuild drops them like other unexpanded works), and the details list it step by step ("which cites" / "which is cited by"), each step selectable. The result is kept for that work and those anchors (`pathSearch` in `App`, with the targets searched), not saved. Measured: _Giant of the Grand Siècle_ to _Jurebassos and linguists_, 4 steps, 201 works searched, about 12 s.
  - **Batched:** neighbors come from the adapter's `getNeighborIds` (one request per 100 works for their references, and `cites:` filters over 100 works at a time, 200 per page, most-cited first, up to 3,000 citing works per call; beyond that the result says `complete: false` and the details note a shorter path is possible). Fetching each work's lists one at a time gave up after 37 works on that example; the batched search took 20-odd requests. Search only uses OpenAlex's links, not Crossref or OpenCitations.
  - **Limits:** at most `PATH_MAX_STEPS` (8) steps and `PATH_MAX_WORKS` (5,000) works searched, and no new level starts after `PATH_TIME_MS` (18 s), inside Heroku's 30-second request limit. Outcomes: `found`, `none` (one side ran out of works: nothing links them on OpenAlex) or `budget`.
  - **Missing records:** reference lists can name works OpenAlex no longer has (deleted or merged; `W4285719527` was the first meeting point on the example). Worse, `cites:` with such an ID matches nearly every work (about 4.9 million), even alongside valid IDs. So `getNeighborIds` sends only IDs its reference lookup found to `cites:` and reports the rest as `missing`, and the search drops them; works on candidate paths are verified when their counts are looked up, and if any are gone the search drops them and continues.
- **Filters:** filters hide nodes from the view. They don't remove nodes from the graph or stop them being fetched. Keep the graph data separate from what is visible. Available filters: year range, minimum in-graph connections (works on the graph that cite it or that it cites, counted once each: `inGraphConnectionCounts`; the slider runs from 1 to the most links of any work but the anchor, which is always shown and would leave most of the range empty, with − and + buttons that step it by one) and source type. Source type is an exclusion list (`excludedTypes`), so types that first appear after expanding a node are shown.

## Data sources

Combining several citation databases to fill each other's coverage gaps is the app's main value, especially for humanities scholarship that any single source covers poorly. Development starts with one provider (OpenAlex or Semantic Scholar). Design for several from the beginning:

- **Tracer IDs:** each source has its own Tracer ID. A mapping record links it to the source's IDs in each provider (OpenAlex ID, Semantic Scholar ID, DOI, and so on). The client and the database use only Tracer IDs, never a provider's ID as the primary key. Deduplication across paths and across providers goes through this mapping.
- **Provider adapters:** put each external API behind a common interface that returns Tracer's own normalized types. Provider-specific response shapes must not leak outside the adapter.
  - **Implemented:** `server/src/providers/`. `types.js` defines the `Provider` interface (`getWork`, `getWorks`, `getCitingWorks`, `getCitedWorks`, `searchWorks`) and the normalized `ProviderWork` type. `ids.js` has `normalizeDoi`, which every adapter must use so DOIs match across providers. `openalex.js` is the first adapter.
  - Adapters return provider IDs, not Tracer IDs. Each `ProviderWork` carries `externalIds` (DOI and others) for cross-provider matching, and `referencedIds` for drawing in-graph edges without extra requests.
  - Adapters are factories (`createOpenAlexProvider({ apiKey, fetch, sleep })`). Tests inject a fake `fetch` and `sleep`; they never call the real API.
  - **OpenAlex costs** (credits per request): single-work lookup 0, list or filter 1, search 10. The keyless daily budget is 1,000 credits; an `OPENALEX_API_KEY` gives 10 times that. Prefer batched `openalex:A|B|C` filters (up to 100 IDs) over many separate list requests.
  - **Record versions:** each stored provider record (`records.<provider>`) has a `version` (`RECORD_VERSION` in `workService.js`; none is 1). A record from an earlier version lacks fields `toWorks` reads, so it counts as expired and is fetched again when next needed (still served if that fails). Bump it, and the client's `SNAPSHOT_VERSION`, when `ProviderWork` or the Crossref record gains a field. 2: language, and Crossref's titles.
  - **Coverage gaps seen:** reference lists are often empty for older humanities articles (e.g. Thompson 1971 has 4,693 citing works but 0 references). Some abstracts are only author and title glued together. OpenAlex's `referenced_works` lists only references it matched to its own works; unmatched ones are dropped from the API entirely.
  - **Crossref** (`crossref.js`) is the second adapter. It only reads reference lists (`getReferences(doi)` → `ProviderReference[]`), which publishers deposit there, including entries OpenAlex couldn't match. Coverage depends on the publisher: Cambridge and Taylor & Francis deposit them; OUP, Duke, Wiley and Project MUSE often don't. Entries are structured (author surname, year, title) or printed text only (`unstructured`; the year is taken from the text). The public pool allows one request at a time, so the adapter queues them. `CROSSREF_MAILTO` moves them to the faster polite pool.
- **Merging:** when providers disagree or one is missing data, merge records and citation edges rather than picking one provider wholesale. Keep track of which provider each piece of data came from.
  - **OpenCitations** (`opencitations.js`) is the third adapter. It supplies open (CC0) citation links, not records: `getCitingIds(doi)` and `getCitedIds(doi)` return the other end's IDs (`LinkedIds`: OpenAlex ID and DOI). Responses for much-cited works take several seconds (about 7 s for Thompson's 3,078 links), so requests time out after 20 s and run at most two at once. `OPENCITATIONS_ACCESS_TOKEN` is optional. Measured gains are modest but real: 4 citing works OpenAlex doesn't link for one Taylor & Francis article, none for others.
  - **Reference lists** are merged: `getCitedWorks` also resolves the work's Crossref reference list (`resolveReferences`, cached on the Source for 30 days). References with a DOI OpenAlex has (looked up in batches with `getWorksByDoi`) become ordinary works, recovering citations OpenAlex didn't link. The rest become reference-only Sources. A Crossref failure is logged, and the OpenAlex references are still returned.
  - **Citation links** are merged too (`linkedExtras`): links OpenCitations has between a work and works OpenAlex has but doesn't link are resolved to OpenAlex records (by OpenAlex ID, else DOI). At most `MAX_LINKS` (300) per work and direction are checked, about 3 OpenAlex credits. Extra citing works join OpenAlex's list most-cited first, within `limit`; extra cited works join the Crossref-found extras. Each recovered link is stored on the citing work's Source, so its edge draws wherever that work appears. Links to works OpenAlex doesn't have are dropped (OpenCitations gives no metadata; its Meta API could). A failure or timeout falls back to OpenAlex alone.
  - **Citation matching:** Crossref's `searchCitation(text)` (`query.bibliographic`) returns candidate works (`CrossrefWork`: DOI, title, authors (or editors, for edited books), year, type, venue, URL) for a reference-only work, sent as its printed text or its fields joined (`citationQuery`). The search always returns something, so `matchCitation` (`works/citationMatch.js`) checks each candidate: same title (or, for a printed citation, the title found inside it, 8+ characters), year at most one off, and the cited first author as the candidate's **first** author (or, printed, named in the text). Reviews are the trap: they carry the book's title, JSTOR's records list the reviewer then the book's authors, and Choice's list nobody. So a candidate without authors matches only a reference without them (long title, agreeing year), and a reference with no venue (a book) can't match a `journal-article`. A reference to a chapter that gives only the book's title (as Cambridge often deposits) doesn't match the book, by design. `GET /api/works/:id/match` returns `{ match }` (or null; works on OpenAlex and references with a DOI aren't searched), with `links` from `doiLinks`: the DOI, plus JSTOR's stable URL for a `10.2307/` DOI (reference-only works with such a DOI get it too). Cached on the Source as `citationMatch` (misses too) for 30 days (`DEFAULT_TTLS.citationMatch`); a failure gives the cached match or null. Measured on _The Dutch Overseas Empire_'s 198 reference-only works without a DOI: 4 matches, all correct (most of its references are books and Dutch sources Crossref doesn't have). When OpenAlex has the match's DOI (looked up with `getWorksByDoi` if need be) and its record agrees with the match (`sameWork`), the grey node is merged into that work (see Duplicate merging below), and the route also returns `work`, the merged work, which the client puts in the grey node's place. The lookup is recorded on the match (`citationMatch.mergeChecked`), so it isn't repeated until the match is refreshed.
  - **Internet Archive** (`internetarchive.js`) is the fourth adapter. It finds scanned copies of a work, linked from its details, not citation data: `searchTexts(words)` queries archive.org's advanced search (no key) for texts with those title words and returns `ArchiveItem`s (`identifier`, `title`, `creators`, `year`, `access`: `open`, `borrow` (controlled lending) or `print-disabled`, `url`). The Archive has no DOIs for most books, so `matchArchiveItems` (`works/archiveMatch.js`) matches by title and author: same main title (before a subtitle, ignoring "&"/"and", a leading article and parenthetical notes), and the first author's surname among the item's creators. An item without creators matches only on the whole title, 20+ characters. Editions are all matches, open first, then by closeness in year; at most 5. Reference-only works are checked by their deposited title and author. One deposited only as printed text (no `citation.title`) is searched by its first 8 distinctive words across all metadata (`printedSearchWords`, `searchTexts(words, { anyField: true })`: no page markers, "op. cit.", common places or publishers, all words required, so a note citing several works finds nothing), and an item matches if its main title (10+ characters) and a creator's surname both appear in the text (`matchArchiveItemsInText`); the details name the item, since a note can cite several works. Measured on 60 random printed citations: 1 match, correct (most are archival sources, short cites, articles or multi-work notes, which archive.org doesn't have as such). It runs only when a work's details open (`GET /api/works/:id/archive`), and the result is cached on the Source as `records.internetarchive.data.items` for 30 days (`DEFAULT_TTLS.archive`). That record isn't listed in the work's `providers`. A failure gives the cached items or none, never an error. (IA Scholar and fatcat, which match articles by DOI, were unusable when this was built: one sits behind a bot check, the other timed out.)
  - **Wikidata** (`wikidata.js`) is the fifth adapter. It supplies authors' names in their own scripts, not citation data: `findByDoi(doi)` (Wikidata stores DOIs in upper case) and `findByOrcid(orcid)` find items through the Action API's search (`haswbstatement:`), `getWorkCredits(item)` reads a work's credited authors (P50, with their place, P1545, and name as printed, P1932), and `getPeople(ids)` their labels, aliases, native name (P1559), kana reading (P1814), languages (P103, P1412), citizenship (P27, for a few countries) and ORCID and VIAF IDs (`WikidataPerson`). Wikimedia throttles clients without a contact address in their User-Agent (a generic one got 429s within a few dozen requests), so set `WIKIDATA_CONTACT`; requests run two at a time, and 429s, 5xx and dropped connections are retried. Live SPARQL isn't used: since 2025 scholarly articles are in a separate graph. `getAuthorNames` (`GET /api/works/:id/authors`, run when a work's details open, not for reference-only works) matches the work's authors to people (`matchAuthors` in `works/authorNames.js`): by ORCID, or a credited author whose name agrees (`sameName`: a surname among the other's words, so family-name-first romanizations match; for other scripts, the same characters in any order), the one at the same place first. There's no search by name, which can't tell apart the four Japanese people named Masao Maruyama. `otherNames` gives what to show beside each name: their name in their own script when the name shown is in another (the native name; else their label in a language they wrote in, else in their country's, only if it looks native, e.g. a Japanese one has kanji, since katakana labels like エドワード・P・トムスン are transliterations of foreign names), with its kana reading, and a romanization (the English label) when the name shown isn't in Latin script. So Thompson gets nothing, though Wikidata has his name in Japanese and Russian. The details panel shows them in the authors line ("Masao Maruyama (丸山眞男 · まるやま まさお)", with `lang`), Wikidata and VIAF links under Links, and "Authors' names in other scripts from Wikidata" under where the data comes from. Cached on the Source as `records.wikidata.data.authors` for 30 days (`DEFAULT_TTLS.authorNames`), not listed in the work's `providers`; a failure gives the cached names or none. Measured: on Thompson's article, a Wikidata and VIAF link and no other names; on a 2014 Japanese article (10.15027/39933), "Kazuya NAGASAWA (長澤和也)", from his label and citizenship, as bots create researchers' items.
  - **Otherwise not yet implemented.** OpenAlex is the only source of work records. `toWorks()` in `server/src/works/workService.js` is where records will be merged.
- **Duplicate merging** (`server/src/works/merges.js`): Sources that are the same work are merged: two OpenAlex records with one DOI (checked whenever works are saved, `mergeDuplicates`; the most-cited becomes canonical), a reference-only work Crossref matched to a work OpenAlex has (`mergeMatched`), and a reference-only work made for a DOI before OpenAlex had it (`d:<doi>`, when a reference list next resolves the DOI; `mergeReferenceOnlyByDoi`).
  - **Conservative:** a shared DOI or a Crossref match isn't enough; `sameWork` must agree too: same title (or one is the other without its subtitle, 12+ characters), years at most one apart, compatible types (a review, erratum, chapter and so on never matches another type, nor a book an article; Crossref's type names are mapped to OpenAlex's) and, when both list authors, a surname in common. A book and a review of it share a title, and a wrong merge loses a work from every graph it's on, which damages trust more than a visible duplicate.
  - **Stable IDs:** the merged Source isn't deleted. It gets `mergedInto` (with `mergedAt` and `mergeReason`: `doi` or `citation-match`) and keeps its IDs and records, so every lookup by its Tracer ID, OpenAlex ID or DOI finds it and follows the redirect (`findSource`, `loadSource`, `toWorks` through `canonicalSources`; `canonicalIdMap` for lists of IDs). Merging a Source repoints those merged into it, so redirects are one hop.
  - **Combined citations:** a canonical work's `references` include those of the Sources merged into it, references to a merged Source point to the canonical one, its `citedByCount` is the sum of its records' (duplicates split their citations), its citing list combines each record's (most-cited first, within `limit`), and its cited list each record's references. Every `Work` has `mergedIds`, the Tracer IDs merged into it.
  - **Saved graphs:** opening one (`GET /api/graphs/:id`) rewrites its anchors, expansions, pins and note targets to the works they were merged into (`redirectMerged`; IDs that became one are kept once, two notes on them joined), saved without changing `updatedAt`, and drops a snapshot holding a merged work, so the rebuild shows it once.
  - **Client:** a work arriving with `mergedIds` replaces those works wherever they are on the graph (`addWorks` → `foldAliases` in `graphModel`): works, references, relations (an anchor stays one), expansions, sticky works and anchors, recorded as `graph.aliases`. `App` then moves pins, notes and the selection to the canonical work. `mergeWork` in the hook takes the work a citation match merged into.
  - **Not merged:** works with different DOIs (a reprint, a translation), a chapter and its book, and duplicates only Semantic Scholar or another future provider would reveal.

## MongoDB roles

1. Cache provider responses, to stay under rate limits and speed up repeat lookups.
2. Store accounts and sessions (see Accounts), and user-built graphs (see Saved graphs).
3. Maintain an internal database of sources, ID mappings and citations merged from all providers. This merged database is the reason MongoDB is in the stack, not just a cache.

Models are in `server/src/models/`:

- **`Source`:** one per work. Its `_id` is the Tracer ID; a duplicate merged into another keeps it and redirects (`mergedInto`; see Duplicate merging). It holds `externalIds` (`openalex` is unique; `doi` is indexed but not unique) and `records.<provider> = { data: ProviderWork, fetchedAt }`. A Source with no records is a **stub**. Saving a work upserts a stub for every work it references, so references get Tracer IDs immediately. That keeps edges intact when A is fetched before B, and keeps a Tracer ID stable when a stub is later filled in.
  - A **reference-only** Source has no records. It holds `citation` (the `ProviderReference`) and `externalIds.citation`, a unique key from `citationKey()`: DOI, else first author, year and title, else the printed text, all case-, accent- and punctuation-insensitive. Works citing the same thing share one Source. A DOI is kept in `citation`, not `externalIds.doi`, so DOI lookups find OpenAlex records first.
  - `records.crossref.data = { tracerIds, referenceOnly }` on a citing Source is its resolved reference list, and `records.opencitations.data.tracerIds` holds works it cites according to OpenCitations. `toWorks` appends every non-OpenAlex record's `data.tracerIds` to the work's `references`.
  - Stubs are created in bulk: `saveWorks` finds which referenced works already have Sources in one query and `insertMany`s the rest, ignoring duplicate-key errors from concurrent saves. One upsert each took about 5 ms apiece, which made a 200-work citing list take nearly two minutes.
- **`CacheEntry`:** cached list results (citing works, searches) stored as ordered provider IDs under keys like `openalex:citing:W1:50`. A TTL index on `expiresAt` deletes old entries, and reads also check `expiresAt`. Cited lists aren't cached, because a work's own record already has its references.

Refresh intervals (`DEFAULT_TTLS` in `workService.js`): work records 30 days, Crossref reference lists and OpenCitations cited links 30 days, citing lists (including OpenCitations citing links, cached as `opencitations:citing:<doi>`) 7 days, searches 1 day. If a refresh finds nothing, stale data is served.

Tech stack: Tracer is a MERN app managed as npm workspaces: React 19 + Vite in `client/`, Express 5 + Mongoose in `server/`. It deploys to Heroku as a single dyno. Both packages are ES modules (`"type": "module"`), and Node 24.x is required.

## Architecture

- **Dev:** two processes. Vite proxies `/api/*` to `http://localhost:5000` (`client/vite.config.js`), so client code always calls relative `/api/...` URLs and never hardcodes a host. The proxy keeps the browser's `Host` header (`changeOrigin: false`): the auth routes compare it with `Origin`, and Vite's string shorthand would rewrite it to `localhost:5000`, refusing every login as cross-site.
- **Production:** one process. When `NODE_ENV=production` (Heroku sets this by default), Express serves `client/dist` as static files and sends `index.html` for every non-`/api` route as an SPA fallback. New API routes must live under `/api` and be registered _before_ that fallback in `server/src/app.js`.
- **Server entry split:** `server/src/app.js` exports `createApp({ workService })`, which has no side effects. `server/src/index.js` connects to Mongo, builds the OpenAlex provider and work service, and calls `listen`. Tests call `createApp` with their own dependencies.
- **Works API** (`server/src/works/`): `routes.js` is thin; `workService.js` does lookup, caching and Tracer ID translation.
  - `GET /api/works?q=&limit=` searches, returning `{ works }`.
  - `GET /api/works/search?any=&title=&author=&abstract=&fulltext=&venue=&publisher=&fromYear=&toYear=&types=&language=&minCitations=&openAccess=true&sort=&limit=&page=` is the advanced search: `{ works, total }`, one page and how many match in all. `venue` and `publisher` are comma-separated IDs from the suggest route, `types` comma-separated work types, `language` a 2-letter code, `sort` one of `relevance`, `cited`, `newest`, `oldest`. At least one field must be given (`parseCriteria` in `routes.js`); pages past the 10,000th result are refused. The adapter turns the criteria into one OpenAlex filter (`advancedSearchParams`), which costs list credits (1), not search credits (10). Cached like searches, with the total (`CacheEntry.total`).
  - `GET /api/works/suggest/venue?q=` and `GET /api/works/suggest/publisher?q=` return `{ suggestions }` (`{ id, name, hint, worksCount }`), from OpenAlex's free autocomplete. The IDs are OpenAlex's (`S…`, `P…`), opaque to the client. Not cached. Both routes are registered before `/:id`.
  - `GET /api/works/:id` returns `{ work }`.
  - `GET /api/works/:id/citing?limit=` and `GET /api/works/:id/cited?limit=` return `{ works }`. Cited works are OpenAlex's references, then more found by DOI in the Crossref list (together up to `limit`), then up to `limit` reference-only works. Reference-only works get their own allowance, so they appear even for works with many matched references. Both lists are empty for a reference-only work.
  - `GET /api/works/:id/match` returns `{ match, work? }`: for a reference-only work, the work Crossref matches its citation to, with links (see Data sources), and `work` when it was merged into a work OpenAlex has (see Duplicate merging). The details panel shows it under the citation, and its DOI and JSTOR links under Links.
  - `GET /api/works/:id/path?to=` returns `{ path, searched, outcome, complete }`: the shortest path of citations from `:id` to `to`, or to the nearest of several comma-separated works (up to 6; see "Path to the anchor"), each step `{ work, link }` where `link` says how the step before relates to it (`cites` or `cited-by`), or `path: null`. 400 without `to`, with more than 6, or with `:id` among them.
  - `GET /api/works/:id/authors` returns `{ authors }`: the work's authors Wikidata knows, each `{ index, name, wikidata, otherNames, links }` (see Data sources).
  - `GET /api/works/:id/archive` returns `{ items }`: copies of the work on the Internet Archive (see Data sources). The details panel lists them under Links with their year and access.
  - Reference-only `Work`s have `type: 'reference-only'`, `providers: ['crossref']`, empty `references` and `referenceProviders`, and `citation` (the printed text, if deposited).
  - `:id` may be a Tracer ID, an OpenAlex ID or URL, or a DOI. **DOIs must be URL-encoded**, since they contain `/`.
  - `limit` must be 1–200 and defaults to 50.
  - Responses are client-facing `Work` objects whose `id` and `references` are Tracer IDs.
  - Errors are returned as `{ error }`:

    | Status | Meaning                                        |
    | ------ | ---------------------------------------------- |
    | 400    | Bad ID or bad limit                            |
    | 403    | Not in the user's plan (see Entitlements)      |
    | 404    | Work not found                                 |
    | 502    | Provider failure                               |
    | 503    | Provider rate limit, or no database connection |

- **Accounts** (`server/src/auth/`): email-and-password sign-up, log in and log out. No saved graphs yet.
  - `POST /api/auth/signup` and `POST /api/auth/login` take `{ email, password }` and return `{ user, entitlements }` (`user` is `{ id, email, plan }`) with a session cookie; `POST /api/auth/logout` ends the session (204); `GET /api/auth/me` returns `{ user, entitlements }`, with `user: null` and the anonymous plan's entitlements when signed out. Statuses: 400 bad email or password, 401 wrong credentials, 409 email taken, 415 not JSON, 403 cross-site, 429 rate-limited, 503 no database.
  - **Models:** `User` (one per account, unique lowercased `email`) and `Identity` (one per sign-in method: `provider` + unique `subject`, plus `passwordHash` for `password`). Keeping them separate is what makes ORCID or Google easy to add: a new `provider` value and OAuth routes that find or create the account, then call `authService.startSession` like `logIn` does.
  - **Passwords:** scrypt from `node:crypto` (`auth/password.js`), stored as `scrypt$N$r$p$salt$hash` so the cost can be raised later; 8–256 characters. A login for an unknown email checks against `DUMMY_HASH`, so it costs the same as a wrong password and gets the same 401: logins don't reveal who has an account (sign-up's 409 does, as usual).
  - **Sessions:** a random 32-byte token in an httpOnly, SameSite=Lax cookie (`tracer_session`, Secure in production), lasting `SESSION_TTL_MS` (30 days). Only its SHA-256 is stored (`Session._id`), and a TTL index removes expired ones. `loadUser(authService)` attaches `req.user` (an account with `plan` and `planOverrides`; `clientUser` is what's sent), used by the works routes for entitlements. The app trusts Heroku's proxy (`trust proxy`) for `req.ip` and HTTPS.
  - **Request checks:** POSTs must be JSON and, when the browser sends an `Origin`, same-origin; with SameSite that blocks cross-site form posts. Rate limits (`auth/rateLimit.js`, in memory, fine for one dyno): 30 logins per IP and 10 per email per 15 minutes, 10 sign-ups per IP per hour.
  - **Password reset (not built):** add a short-lived, single-use token stored hashed like sessions, a route that emails a reset link (needs an email service), and one that sets a new `passwordHash` and calls `authService.endAllSessions`.
  - **Client:** `useAuth` (`client/src/auth/`) checks `/api/auth/me` on load (`user` is undefined until then); `AccountMenu` in the header shows "Log in" and "Sign up" or the email and "Log out", with a modal form for logging in and signing up.
- **Entitlements** (`server/src/entitlements/`): what each plan includes, checked on the server by every gated route, and shown on the client by every gated control. Every tier includes every feature that exists, and only the `anchors` limit differs (2, or 6 on Scholar); billing (Stripe) comes at launch and will set `User.plan`.
  - **Plans** (`plans.js`, `PLANS`): `anonymous` (signed out), `free` and `scholar` (`User.plan`, default `free`; an unknown value counts as `free`). Each has **features** (`saveGraphs`, `autoSave`, `coCitations`, `pathSearch`, `advancedSearch`) and **limits** (`depth`, `perNode`, `maxNodes`, `savedGraphs`, `anchors`). Signed out, everything but saving is included. `User.planOverrides` (`{ features, limits }`) changes one account's, e.g. for testers; unknown keys and wrong types are ignored.
  - **Checks** (`entitlements.js`): `entitlementsFor(user)` resolves plan plus overrides; `can(user, feature)` and `limitFor(user, limit)` throw on an unknown key, so a typo can't grant access. `requireFeature(feature)` (middleware) and `checkLimit` throw `EntitlementError`, a 403 whose body names it: `{ error, feature }` or `{ error, limit }` (`HttpError`'s `details`).
  - **Where:** `/api/works/search` needs `advancedSearch`, `/:id/path` `pathSearch`; `/:id/citing` and `/:id/cited` cap `limit` at `perNode` (and default to it if smaller), while search pages don't. Saving a graph (`POST`, `PUT /api/graphs/:id`) needs `saveGraphs`, within `savedGraphs`, `anchors` and the option limits (`checkState(state, limits)`); listing, opening, renaming and deleting don't, so an account that loses it keeps its graphs.
  - **Client** (`client/src/auth/entitlements.js`): `useAuth` keeps the entitlements from the auth routes, with `can(feature)` and `limits`; until they arrive (or if they can't), it uses `ANONYMOUS`, a copy of the server's anonymous plan that a test keeps in sync. `App` keeps build options within the limits (`clampOptions`; the URL, saved graphs and the form are clamped too, and the form's depth and size go no further), and disables what the plan lacks with "Not included in your plan": Advanced search, Find Co-Citations, Find shortest path, Save graph and Auto-save.
  - **Not enforceable:** builds run in the browser as many `/citing` and `/cited` requests, so depth, `maxNodes` and co-citations are only enforced by the client; the server sees single requests. Enforcing graph size would need a per-user request budget on the works routes, or builds on the server.
  - **Adding a gated feature:** add its key to every plan in `plans.js` (and to `ANONYMOUS` on the client), check it in its route with `requireFeature` or `checkLimit`, and in its control with `auth.can`.
  - **Plans and pricing page** (`PricingPage`, at `/pricing`, linked from the header as "Plans and pricing"): a table of every feature, built or planned (from ROADMAP.md), with what Free and Scholar get (included, not, or a limit such as "Up to 2") and a status, "Available" or "Planned"; planned rows are muted. The rows are data in `client/src/pricing/features.js` (`FEATURE_GROUPS`), grouped by heading; the free anchor limit comes from `ANONYMOUS`. When a feature ships or a plan changes, update that file too. No prices are shown: Scholar isn't on sale yet. The table scrolls sideways inside its box on narrow screens (the box is `position: relative`, so the cells' visually hidden labels stay inside it rather than widening the page).
- **Saved graphs** (`server/src/graphs/`, model `SavedGraph`): a signed-in user can save the current graph, reopen it, rename it and delete it.
  - **Stored:** what's needed to rebuild the graph, not its works: `anchors` (each `id` = Tracer ID, plus `ref` = DOI/OpenAlex ID and `title` as fallbacks; primary first, 1 to 6), `options`, `filters`, `view` (`axisAngle`, `pinned`), and `expanded`, the sticky works in the order the user expanded them (a later expansion can depend on an earlier one's works). Its `_id` is the ID used to open it, `?graph=<id>`. `version` is for changes of shape: version 1 stored a single `anchor`. Those are read through `anchorsOf` (`anchors`, else `[anchor]`), the API returns only `anchors` (summaries too), and their next save rewrites them as version 2 (`anchor` unset). A state with a single `anchor` (an older client) is accepted as `anchors: [anchor]`. A blank name becomes the anchors' titles (`anchorsName`: one title, two joined by "&" or the first "and N more", shortened to fit 120 characters; the client's default name is the same).
  - **Snapshots (cache):** `GraphSnapshot` (same `_id` as the saved graph) holds the graph as built, gzipped JSON from `graphSnapshot` in `graphModel` (works, relations, expanded directions, sticky, `truncated`), so reopening it fetches no works. It's used for `SNAPSHOT_TTL_MS` (one week; TTL index on `expiresAt`, and reads check it too) and only while its `key` matches the graph's `stateKey` (a hash of anchors, options and expanded; filters, view and name don't count; one anchor hashes as its ID alone, as in version 1, so those snapshots stay valid). Snapshots have a `version` (`SNAPSHOT_VERSION` in `graphModel` and in `graphService`, kept equal by a test; one without is 1): opening a graph drops a snapshot older than the server's, since its works lack data the client now shows (2: `referenceProviders`; 3: language and other titles), and the graph is rebuilt. Bump both when works gain such data. A snapshot must be of the same anchors in the same order (`anchorIds`; one from an older client's `anchorId` counts as one). Saving sends a snapshot of the graph on screen (none while a run or expansion is in progress). An update without one drops the old snapshot if the state changed. Opening a graph with no fresh snapshot rebuilds it, then `PUT /api/graphs/:id/snapshot` (`{ key, snapshot }`) stores the result; a 409 means the graph was saved since with another state. Snapshots can be megabytes, so the graphs router is mounted before the global 16 kB JSON parser and parses its own bodies (25 MB) after `requireUser`.
  - **Annotations:** notes on works are saved as `annotations`. Each one has a `target` (`{ type: 'graph' }` or `{ type: 'work', workId }`), a `kind` (`note` for now; highlights or tags later) and a `body` (up to 10,000 characters), so notes on works and on the graph share one list; only notes on works have a UI so far. The client sends them all as `state.annotations` (`checkAnnotations`: one per target, the last winning, blank ones dropped), and `GET /:id` returns them with IDs and timestamps. A `PUT` with `annotations` replaces them, keeping unchanged ones as they were (`replaceAnnotations`); without the field it keeps them. They don't count toward `stateKey`, so changing a note keeps the snapshot.
  - **API**, all for the signed-in user's own graphs (401 when signed out; another user's graph is a 404): `GET /api/graphs` (summaries, newest first), `POST /api/graphs` (`{ name?, state, snapshot? }`), `GET`/`PUT`/`PATCH` (rename)/`DELETE /api/graphs/:id`, `PUT /api/graphs/:id/snapshot`. `GET /:id` adds `stateKey` and `snapshot` (or null). `checkState` validates the state (option ranges as in `urlState.js`); a blank name becomes the anchor's title; at most the plan's `savedGraphs` (500), and options within its limits (403 beyond). The routes reuse auth's `sessionRequestChecks` (database, JSON POSTs, same-origin changes) and `requireUser`.
  - **Client:** the "Save graph" button (`SaveGraph`, top right of the canvas) opens a dialog to name it; a graph opened from (or saved as) a saved graph offers "Update" or "Save as new". Saving adds `?graph=<id>` to the URL. Opening one (`openSaved` in `App`, `restore` in `useCitationGraph`, `restoreGraph` in `graphModel`) sets its options, filters and axis, then loads the snapshot if there's one; otherwise it builds from the anchor, then re-expands the saved works in order, fetching any the build didn't reach. A new search, or a run writing the anchor URL, drops `?graph`.
  - **Auto-save:** an "Auto-save" checkbox beside "Save graph" saves every change to the saved graph as it happens (`App`: `saveState`, `saveNow` and an effect). Turning it on for an unsaved graph saves it at once, named after the anchor. A change is anything in the saved state (options, filters, axis, pins, notes, expansions) or the graph's works (a co-citation search, a path); it's sent once the graph is idle (no run or expansion) and changes have settled for `AUTO_SAVE_DELAY_MS` (1.5 s), one save at a time. A snapshot goes with it only when the works changed, since an update without one keeps the server's (the `stateKey` is unchanged). Opening a saved graph takes what it builds as saved (`lastSaved.baseline`), so reopening doesn't save. It's remembered per saved graph in `localStorage` (`tracer:autoSave:<id>`), and a new search turns it off. The status beside it reads "Saving…", "All changes saved" or "Couldn't save: …"; after a failure the next change tries again.
  - **Profile page** (`ProfilePage`, at `/profile`, linked as "My graphs" in the header): lists saved graphs with open (a link to `/?graph=<id>`), rename and delete (with a confirmation). `App` picks the page from the path (`/profile`, `/pricing`, else the graph); there's no client-side router, so moving between pages reloads, and the server's SPA fallback serves `index.html` for `/profile`.
- **MongoDB version:** use 8.2. MongoDB 8.3+ refuses to start on Linux kernel 6.19 and later ([SERVER-121912](https://jira.mongodb.org/browse/SERVER-121912)), and this dev machine runs kernel 7.0. That's why the Docker image is `mongo:8.2`, and why root `package.json` pins `config.mongodbMemoryServer.version` for tests. Don't bump either to 8.3+ until that bug is fixed.
- **Works tests** (`works.test.js`) use `mongodb-memory-server` (a real `mongod`, downloaded to `~/.cache` on first run) and a fake provider backed by an in-memory catalog. They assert on provider call counts to verify caching, and inject `now` to test expiry.
- **Client** (`client/src/`):
  - **`graph/graphModel.js`:** pure graph logic, independent of React.
    - The graph is `{ anchorIds, works: Map, relations: Map, expanded: Map }` (`isAnchor`, `sameAnchors`).
    - `relations` records how each work joined: `anchor`, `citing` or `cited` (relative to the anchor it was first reached from).
    - Cited works found for a work are merged into its `references` (`addFoundWorks`): a work's cited list is its reference list, and it can include works its own record didn't have when first fetched (reference-only works).
    - `expanded` records which directions have been fetched for each work.
    - `sticky` holds works that keep their neighbors across re-anchoring. `expandWork` (user expansion) adds to it, and `reanchorGraph` adds outgoing anchors (but not those in `unstick`, an anchor being removed). Build traversal never makes a work sticky; if it did, re-anchoring could never drop anything.
    - `reanchorGraph(graph, anchorIds, …, { unstick })` reuses the anchors' data (no `getWork`), runs `buildGraph`, then re-expands each sticky work. Neighbor lists are fetched again rather than tracked, which is cheap because the server caches them. A sticky work the new build didn't reach is recolored relative to the new anchors (`relationTo`: the first anchor with a direct citation, else years against the primary).
    - Edges (`deriveEdges`), in-graph counts and node sizes (`totalCitationCounts`) are always calculated from `works`, never stored.
    - `buildGraph(anchorIds, …)` runs breadth-first with a separate depth per direction, from all anchors at once (looked up in parallel; two IDs naming one work make one anchor). Levels alternate between directions so `maxNodes` doesn't starve one of them, and requests run with limited concurrency. `expandWork` returns an updater to apply to the latest state.
  - **`graph/useCitationGraph.js`:** holds graph state. A new build or re-anchor aborts the one in progress (`AbortController`). A re-anchor keeps the old graph on screen and swaps in the result once (status `reanchoring`, with `progressCount` for the status line), so kept nodes hold their positions. If it fails, the old graph stays.
  - **Loading progress** (`graph/progress.js`, `components/LoadingProgress.jsx`): builds, re-anchors and expansions each report to a tracker, which counts work in API requests.
    - `plan` adds requests known to be coming. Each real request is timed with `begin()` and its returned finish function. `complete()` marks planned requests that were skipped (for example, when the graph is full), so `done` always reaches `total`.
    - `project` estimates requests on deeper levels from the new works per request seen so far, scaled down to fit `maxNodes`.
    - Time remaining = remaining requests × average request latency ÷ parallelism (4 for builds, 2 for expansions, roughly 3 for re-anchors). Latency is measured per request rather than by wall clock; a wall-clock rate overestimated about 4× while early requests ran one at a time.
    - Separately from the counts, the tracker lists requests by `{ key, label }`: `queue` adds known upcoming ones (a build level's frontier, an expansion's works, a re-anchor's sticky works), `begin(request)` moves one to running, `dequeue` drops a skipped one. Each card lists them under "In progress" and "Queued" (first 5, then "and N more").
    - The hook keeps one entry per task in `tasks`. The visible cards update on every request, but the `role=status` line changes only on start and finish, so screen readers aren't flooded.
  - **`graph/GraphView.jsx`** renders with `react-force-graph-2d` (canvas).
    - Node objects are reused across updates, because force-graph stores positions on them.
    - Filtered-out works stay in the simulation and are hidden through `nodeVisibility`/`linkVisibility`, so filtering doesn't reshuffle the layout.
    - **Node size:** radius = `NODE_MIN_RADIUS` (9) + `NODE_GROWTH` (6) × log₁₀(1 + total citations). Totals run from 0 to thousands, so the log keeps a classic from dwarfing everything: 10 citations give a radius of about 15, 100 about 21, 1,000 about 27. The minimum keeps every circle big enough for its source-type icon. It's passed as `nodeVal` = radius² with `nodeRelSize` 1, so arrowheads and hit areas stay on the circle's edge.
    - Colors come from CSS custom properties in `App.css`. The canvas resolves them through a hidden probe element and normalizes them to `rgba()` with a 1x1 canvas, because derived tokens compute to `oklab()`/`color()` strings. It re-reads them when the theme changes.
    - Tooltip HTML is escaped, because titles come from external data.
    - **Year layout:** `graph/axis.js` (`axisGeometry(angle)`) converts between screen x/y and axis coordinates: u along the time axis, v across it. A custom `yearForce` pulls each node to its year's u, with only a weak pull across the axis, so works from the same period spread out. `yearPositions` spaces distinct years in order, giving larger gaps logarithmically more room. Years near the anchors' are further apart: each step is stretched by up to 1 + `FOCUS_BOOST` (3×) at an anchor's year (the largest boost of any anchor's), with the boost halving every `FOCUS_HALF_LIFE` (4) years away, so distant decades stay compact. Re-anchoring moves the focus. Faint lines across the axis label the years (`onRenderFramePre`).
    - **Lanes for unconnected parts:** a work the user expanded or added (from advanced search, say) can bring in works with no citation path to the anchors'. Each connected component (`connectedComponents` in `graph/lanes.js`, ignoring direction, computed from all works, filtered or not; those holding anchors first, in anchor order) gets its own band across the axis: the primary anchor's is centered on it, and the others stack outward on whichever side they're on, `LANE_GAP` (80 × spread) apart (`laneCenters`). The year force pulls each work toward its lane's center instead of the axis, and moves each other component there as a whole (`LANE_PULL`); with one component the layout is as before. New works in a component with no placed works start in a lane of their own, beyond everything, rather than on the axis among unrelated works. The automation hook's `layout()` lists each work's u, v, target u and component.
    - **Rotation:** the angle lives in `App` state (`ViewPanel` slider). On change, `GraphView` moves every node straight to its rotated position (keeping its u and v), instead of letting the simulation drag nodes there, and refits the view. The force reads the current geometry through a ref, so it never needs replacing.
    - **Spacing by graph size:** `layoutSpread(count)` (`graph/spacing.js`) is 1 up to 60 works and √(count / 60) beyond, rounded to steps of 0.25 so a small expansion doesn't shift every work. `COLLIDE_PADDING` is multiplied by it, and repulsion strength and range by its `CHARGE_GROWTH` (0.4) and `CHARGE_RANGE_GROWTH` (0.5) powers. Small graphs span decades along the axis but little across it, so their base repulsion (`CHARGE` −150, range 300) is strong; large ones already fill the view across it, so it grows slowly. Measured: _Manchus and Han_ (41 works) went from 4.2 times as long along the axis as across to 2.7, and Thompson's 21 citing works from a median gap of 0.4 radii to 1.2; a 288-work graph stayed as before (stronger repulsion there halved the size its circles are drawn at). Year spacing isn't scaled, since stretching the axis also stretches empty decades and fitting it shrinks every circle. On a 408-work graph (factor 2.5) the median gap from a circle to its nearest neighbor went from 0.5 to about 2 radii (a 41-work graph: about 1.5). Scaling repulsion by the factor's square overshot (median 3.6; fitted circles became dots). Known issue: year labels sit at the far end of each year line, past the outermost work, so on a widely spread graph they fall outside the fitted view.
    - **Tuning:** layout constants sit at the top of `GraphView.jsx`. Years are packed fairly close (`YEAR_SPACING` 15), and repulsion (`CHARGE`) spreads works across the axis. `YEAR_PULL` keeps that repulsion from moving works along it. Measured on a 41-work graph: median distance from a work's year is about 0.4 years, and no works end up out of chronological order (still none with the stronger repulsion, on that graph and Thompson's).
    - **Forces:** d3's `center` force is removed. It shifts all nodes to keep their average at the origin, which pulls them off their year positions. Links are weak (strength 0.02), because citations always span years and would fight the time axis. Charge has `distanceMax`, so a crowd on one side can't push a node off its year. `forceCollide` stops large circles from overlapping.
    - **Expanded ring:** works whose citing and cited works have both been fetched (by the Expand button or a build's traversal; for a book, its chapters too) get a `--node-expanded` (azure) ring just outside the circle, clear of the selection stroke. `App` computes the set (`expandedIds`) with the same rule as the details panel's "Expanded" button. The legend lists it.
    - **Link widths:** links touching any anchor are thicker (`ANCHOR_LINK_WIDTH` 2.5) than links between other works (`LINK_WIDTH` 0.5). Links to the selected work add `LINK_SELECTED_EXTRA`.
    - **Link drawing** (`graph/linkRouting.js`): `GraphView` draws links itself (`linkCanvasObjectMode` `replace`, with its own arrowheads); force-graph's link layer can only draw single curves. Links aren't interactive, so `linkPointerAreaPaint` is a no-op. `layoutLinks` runs every frame in `onRenderFramePre` and sets `link.route`.
      - **Bundling:** links that share an end node and the same citation direction, and leave that node within `BUNDLE_ANGLE` of each other, share a trunk from the node out to a junction. The trunk is `√n` times as thick as one link and carries the single arrowhead for incoming bundles. Its length is set by how quickly the links diverge (`BUNDLE_GAP`), is capped at `BUNDLE_REACH` (60%) of its shortest link, and stops before any circle in its way. Trunks are drawn before the links (in `onRenderFramePre`).
      - **Merging as far as possible:** `makeBundle` tries leaving out the shortest links (a short link to a nearby work would otherwise cap the whole trunk; left out, it still leaves along the trunk) and `TRUNK_DIRECTIONS` (9) directions within the links' angles (to pass beside a circle instead of stopping at it), and keeps whichever merges the most line length, (links − 1) × reach. Where each direction is first blocked is computed once per bundle. The chosen turn is stored relative to the links' mean direction, so `placeBundle` keeps it as they move. Measured median share of a line that runs merged: 28% → 44% (_Manchus and Han_), 23% → 37% (a 61-work graph), 13% → 22% (408 works, where circles near the anchor still stop most trunks).
      - **Merging where links meet** (`mergeCrossings`): links into the same node merge as soon as they cross or come within `LINK_MERGE_DISTANCE` (a small circle's diameter, 18) of each other, at the meeting furthest from the node (the first contact on the way in). `findCrossings(links, margin, near)` finds these meetings: each link's path from the node (along its trunk, then its curve in `CROSSING_SAMPLES` segments), hashed by cell with numeric keys, each segment pair checked once (in the first cell their padded boxes share), segments inside the node's margin skipped. Meeting on a trunk, the other link joins it there (a per-link join point, `bundle.joins`); meeting beyond a junction, it joins at the junction, the longer trunk winning between bundles; a bundled link brings its whole bundle; two loose links form a bundle whose junction is the meeting, if a straight trunk there is clear. Bundles left with one link dissolve, moved links are re-routed, and up to `CROSSING_PASSES` (4) passes re-check only nodes where something moved. A trunk is drawn in segments (`trunkSegments`), each as thick as the links it carries, and a branch widens to the trunk's width where it joins (`linksAt`). Meetings left after settling: 8 → 1 and 22 → 1 on small graphs, 863 → about 37 on 408 works (mostly pairs whose straight trunk would cross a circle).
      - **Never backwards:** a link may merge only where it keeps heading toward the node: followed from its far end in, its distance to the node must never grow (running parallel is fine; `movesAway`, with `BACKTRACK_TOLERANCE` 0.5 for sampling noise). A join whose point is at least as far out as the link's far end is refused without routing; otherwise the link is joined, re-routed, checked, and if it heads backwards, put back (its saved route restored, not re-routed) and the refusal remembered so later passes skip it. New bundles from two loose links are checked the same way. `releaseBackward` releases backwards members of ordinary bundles before merging and again after it, repeating until none (a link's route can change after its check, when its other end merges or a bundle it was in dissolves). A bundle's turn is re-based on its links whenever they change (`keepDirection`): it's stored relative to their mean direction, which a joining link shifts, and without that the trunk rotated on the next frame and sent members backwards. More meetings stay unmerged as a result (those that would double back), by design; the automation hook's `backwards()` counts merged links that head backwards, and should report 0.
      - **Cost:** a full plan with merging takes about 12–14 ms on small graphs and about 270 ms on 408 works, so it runs only when the layout settles or the works or filters change, never while nodes move. `GraphView` tracks movement with force-graph's `onEngineTick`/`onEngineStop` (not frame timing, which fed back on itself once frames got slow: slow frames looked like pauses and re-planned every frame). While moving it re-plans every `ROUTE_EVERY` frames without merging; on stop it re-renders once for a full plan; later frames only place.
      - **Debugging:** each bundle records what stopped its trunk (`limitedBy`: `divergence`, `shortest` or `circle`), and the automation hook's `window.__tracerAutomation.bundles()` lists bundles with their reach, cause and member lengths.
      - **Branches** leave the junction along the trunk (cubic curve) so they merge smoothly. If that curve would cross a circle, they fall back to routing.
      - **Routing:** a link's free part bends around visible circles instead of cutting through them. `routeLink` picks the straightest quadratic bend that clears every circle by `LINK_CLEARANCE`, up to `MAX_CURVATURE`; past that it crosses the fewest circles.
      - **Performance:** routing runs every frame for every link, so it has to be cheap. `routeLink` merges each circle's forbidden ranges, then sweeps the sorted range ends once to count hits (O(n log n) in nearby circles; checking each candidate against each circle was O(n²)). Nearby circles come from a spatial grid (`createGrid`, `GRID_CELL` 80) built once per frame; it pads each query by the largest radius and falls back to scanning all nodes when a box covers more cells than there are nodes. Links are also re-planned (`layoutLinks`: bundling, trunk reach, bends) only every `ROUTE_EVERY` (4) frames while nodes move. Frames in between call `placeLinks`, which moves the planned routes with their nodes: bends are kept as curvatures relative to each link (or the `tangent` choice), and a trunk keeps its reach along its links' current mean direction. A change to the works or the visible set always re-plans (see "Cost" below for how settling is detected). On a 408-work graph, frames while the layout moves went from about 1.8 s (0.8 fps) to about 17 ms median (41 fps); the larger spacing for big graphs later brought it to about 26 fps, with canvas drawing (rasterization, branch ramps) now the main cost rather than routing. Measure with a CPU profile (Chrome DevTools protocol, unminified build) before optimizing further.
      - **Ramps:** over the last `RAMP_PIXELS` (screen pixels, at most `RAMP_MAX_SHARE` of the branch) before a junction, a branch widens smoothly to its trunk's width, so there's no sudden step. It's drawn as `RAMP_STEPS` short segments of growing width.
      - **Opaque links:** `--graph-link` is translucent, but `useThemeColors` resolves `colors.link` to the opaque color it shows as over the background behind the canvas (`backgroundBehind`). Overlapping links, ramp segments and trunks then look exactly like one link instead of darkening where they stack. The cost is that links hide the faint year lines rather than letting them show through.
      - A selected link redraws its own share of any trunk in the active color, so the highlight runs node to node without marking the whole bundle.
    - The view fits once per run (build, re-anchor or options change; `App` passes a run counter as `fitKey`), after the run finishes and the layout settles. Fitting to a partial graph leaves the view zoomed in on one small part of the time axis. Expansions don't change `fitKey`, so they don't move the view.
  - **Interaction:** clicking a node selects it and opens `DetailsPanel`; expanding is a button there. The anchors, the selected node and pinned nodes always stay visible regardless of filters.
  - **Defaults** (`DEFAULT_OPTIONS` in `urlState.js`): depth 1 each way, 20 works per node, 300 max works. Each extra level multiplies requests, which costs OpenAlex credits.
  - **URL sync** (`urlState.js`, plus effects in `App.jsx`): reading and writing the URL are pure functions. `App` sets `pendingUrl` when a run starts.
    - It **pushes** a history entry for user actions (search or re-anchor), so Back returns to the previous anchors.
    - It **replaces** the entry for runs started from the URL (page load, popstate), so history doesn't fill with duplicates. A URL using an OpenAlex ID is rewritten to the DOI this way.
    - On page load the URL's graph is opened once the account is known (`accountKnown`), since the plan's limits decide how many anchors and how large a build it can ask for; reading it before would apply the signed-out limits.
    - The URL is written only after a run reaches `done`. `idle` means the run hasn't started; on page load the URL effect runs in the same pass that starts the build.
    - Failed builds leave the URL alone.
    - App tests reset `window.location` in `beforeEach`, because jsdom shares it across tests.
  - **Source-type icons** (`graph/sourceTypes.js`): each OpenAlex `type` maps to a label and a lucide icon in two forms.
    - The lucide-react component is used in the DOM: the source-type checkboxes in Filters (which double as the icon legend) and the details panel.
    - `sourceTypeKeys.js` has the type keys and the unknown-to-"Other" grouping with no UI dependencies, so `graphModel` can filter by type without importing icon libraries. A test keeps it in sync with `SOURCE_TYPES`.
    - The vanilla `lucide` element data is converted to a path string (`iconPathData`) and cached as a `Path2D`, then stroked inside canvas nodes. Icons appear once a circle's on-screen radius is at least `ICON_MIN_SCREEN_RADIUS`.
    - Keep `lucide` and `lucide-react` on the same version.
    - Import icons by name, never `import * as`, which would bundle all of lucide.
    - Unknown types fall back to "Other".
    - Icon colors are the `--node-icon-on-*` tokens.
  - **Automation hook:** with `?automation` in the URL, `GraphView` sets `window.__tracerAutomation`, for browser drivers (`/run-tracer`): `nodes()` returns visible nodes' screen positions (with `anchors`, the anchors each is near, when there are several); `bundles()` the merged-line stats; `crossings()` the remaining same-node meetings (crossings or near-misses) by kind; `planMs()` the time for one full link plan; `backwards()` merged links that head back away from their node. It's off by default.
  - **Theming** (`App.css`): three layers.
    1. Five `--palette-*` slots are the only place colors are defined. Swapping them re-themes everything. The current scheme is [coolors.co/588157-ffede1-363537-3185fc-d05353](https://coolors.co/588157-ffede1-363537-3185fc-d05353): fern (cited works), azure (anchor, primary actions), lobster pink (citing works, errors, dark-mode accent), linen (backgrounds) and jet (text, dark-mode backgrounds).
    2. `--ink` (jet) and `--paper` (a linen tint) are the neutrals.
    3. Role tokens (`--bg`, `--accent`, `--node-anchor`, `--graph-link`, …) are derived with `color-mix()`, separately for light and dark.

    Components and canvas code use only role tokens; never put a literal color anywhere else. `accent-color` themes native controls. Nodes get a `--node-outline` that meets 3:1 on its own, so no fill has to. Light-mode `--accent` is azure darkened so white button text meets 4.5:1, and `--error` is lobster pink darkened; in dark mode lobster pink is lightened to serve as the accent. Re-check contrast when changing the palette: resolve the tokens in a browser (they're `color-mix()` values) and compare text pairs against 4.5:1 and node and icon pairs against 3:1.

  - **Client tests** mock `GraphView` (jsdom has no canvas) and `api.js`. To check the real canvas, use the `/run-tracer` skill (`.claude/skills/run-tracer/`). It runs an isolated server on :5099 and a headless-browser driver that can select nodes by color and take screenshots.
- **Heroku build:** `npm install`, then `heroku-postbuild` (client build), then the `Procfile` `web: npm start`. The server reads `PORT` from the environment.
- **Database:** the server calls `listen` first, then connects to MongoDB in the background through `connectWithRetry` (`server/src/db.js`), retrying every 5 seconds. Mongoose never retries a failed _initial_ connection by itself. Until it connects, or if `MONGODB_URI` is unset, `/api/works` returns 503. In dev, a closed API port shows up as a bare **502 from Vite's proxy**, not from Express. `bufferCommands` is off, so queries fail fast instead of hanging. `/api/health` reports `db: connected|disconnected`. The dev script loads `server/.env` with `--env-file-if-exists`; there is no dotenv dependency.
- **Express 5:** path syntax differs from Express 4, e.g. the SPA fallback uses a regex rather than `*`. Async route handlers that reject are forwarded to error middleware automatically.
